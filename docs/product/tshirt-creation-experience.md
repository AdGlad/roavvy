# Proposal — The Best T‑Shirt Creation Experience for Roavvy

**Status:** Discovery + design proposal. **No implementation yet.**
**Author:** Design Studio investigation (2026‑08).
**Core promise to the customer:** *“I designed this T‑shirt. It is unique to me.”*

> This document is the deliverable requested in the *"Design the Best T‑Shirt Creation Experience"* goal.
> It is grounded in a code‑level audit of both the production merch engine and the new Design Studio,
> not in the current UI. Section numbers follow the brief's 23‑part deliverable.

---

## 0. Executive summary

Roavvy already contains **two** procedural design systems:

- **The production merch engine** (`apps/mobile_flutter/lib/features/merch` + `features/cards`): a `DesignParams`
  genome, generated by `ProceduralDesignGenerator`, rendered by the widget‑capture `CardImageRenderer`,
  print‑styled by `PrintStylePipeline`, and exported to print through the `createMerchCart` cloud function +
  Printful (1800×2400 @150 DPI, transparent, front **and** back). It **ships and prints today** and already
  learns implicitly from view/save/select behaviour.
- **The new Design Studio** (`packages/design_forge`, `packages/design_forge_render`, `apps/design_lab`): a pure‑Dart
  **deterministic `DesignRecipe` genome**, a headless `ui.Canvas` render pipeline, SplitMix64 named RNG sub‑streams,
  a real preference‑learning stack, a reproducible design library, and the new delete‑to‑learn loop. It has the
  **better creative brain** but is currently wired into mobile only as the *recommendation/variation/preference*
  layer — it does not yet render or print, has no bundled font, no garment compositing, and no front/back concept.

**Recommendation.** Make the **Design Studio `DesignRecipe` the single reproducible source of truth** for every
customer design, and build the new creation experience directly on it. **Reuse the proven render/print pipeline
behind a `DesignRecipe → DesignParams` adapter** rather than rewriting it, and mature `design_forge_render` toward
print parity over subsequent milestones. This honours the brief's "extend Design Studio, don't bypass it" while
respecting its "unless repository analysis shows a compelling reason" clause — the compelling reason being that the
production renderer already solves fonts, print files, front/back placement, garment‑aware ink and Printful
integration that `design_forge_render` has not yet built.

**Recommended interaction model.** Not a wizard, not a template picker, not a repeated *Generate* button. A
**“Studio Canvas”**: the shirt appears immediately as one strong hero design derived from the customer's travels,
then evolves through a short, rotating series of **meaningful creative decisions** (Direction → Vibe → Focus →
Colour → Words), each of which *immediately transforms the visible shirt* by constraining or re‑rolling **one**
recipe axis while everything else stays stable. A compare tray, per‑axis **lock**, **branch** and free **undo**
(all trivially enabled by deterministic recipe IDs) let customers explore without losing work. Progressive
disclosure exposes finer editing (text, effects, front/back, per‑element nudges) only on demand.

## 2. Detailed findings — the new Design Studio

- **Recipe genome** (`design_recipe.dart`, `recipe_parts.dart`): `DesignRecipe{schema/engine/grammar/assets versions, seed, content, composition, flagCombination?, clip?, edgeTreatment?, palette?, effects?, typography?, motifs[], provenance?}`. Identity is a **content hash** over the artwork‑defining fields only (`recipeId` = FNV‑1a of canonical JSON; provenance excluded). `DesignFamily` has 15 values incl. `passportStamp, timeline, typographic, badge, wordCloud, landmark, journeys, frontRibbon, achievements, stats, tornHero`.
- **Determinism / RNG** (`deterministic_rng.dart`): SplitMix64 with **named sub‑streams** (`.stream(name)`) that are an append‑only contract — adding a draw in one axis doesn't shift another. At generation the axes already draw from distinct streams (`combo/algo/clip/finish/orient`); render stages draw their own (`effects/edge:torn/wordcloud/collage`). **But there is no `DesignRecipe`‑level "re‑roll one axis" API** — the whole design is drawn from one seed inside `LabShowcaseGenerator._one`.
- **Genre / Style / Effects** (`apps/design_lab/lib/lab_styles.dart`): three orthogonal axes — **Genre** (subject: flags/passport/animalsNature/landmarks/maps/travelLog/typography/milestones), **Style** (finish: 13 presets → edge+fx+palette), **Effects** (continuous distress/grain/fade/cracks/halftone/ripple/acidWash/tieDye/shatter). `StyleCluster` is a coarse 6‑bucket grouping used by learning.
- **Render pipeline** (`design_forge_render`): `CanvasRenderer` → composition → clip → edge → effects → colour → flatten (background then artwork) → PNG + `imageHash`. Data‑driven families short‑circuit into `DataLayouts`.
- **Typography**: text can be a **clip mask** (`TextMask`, flag fills the letters). The `Typography` recipe group exists but is **inert — no stage consumes it**. **No display font is bundled** (`pubspec` fonts commented out); headless text falls back to Ahem boxes.
- **Colour/palette**: `Palette{garmentColour?, strategy, accents[], vintageGrade}`; `ColourStage` implements monochrome/duotone/vintage. `garmentAware` strategy is **declared but unimplemented**; preview always uses a fixed grey background — garment colour is modelled but never composited.
- **Country material**: `SvgFlagResolver` rasterises flags; silhouettes/outlines/passport stamps supported; `resolvePassportCollage` builds a shuffled, jittered, per‑country‑inked multi‑stamp page (`PassportInk{flag,black,white}`).
- **Travel model**: `Trip/DateRange/TravelHistory` + `DesignContext{flagCodes,scopeKey,trips,dateRange}`; `RecipeContent.entries/meta` bake travel data into data‑driven recipes so they are self‑contained.
- **Preference learning**: `DesignPreferences` (style/shape weight maps, clamped), `PreferenceLearner` (signals viewed 0.1 … selectedForMockup 0.6, rejected −0.5; `observeBatch`/`featureTally`), `PreferenceScorer`, `DiversitySelector`, `StratifiedSampler`, `LabSmartGenerator`, `VariationGenerator` (single‑axis neighbours), plus the **delete‑to‑learn** loop and reproducible `DesignLibrary`.
- **Quality**: no standalone aesthetic scorer; "quality" is only an *input* to `PreferenceScorer.combined`. Guardrails are diversity constraints, exploration floors, and rejection learning.
- **Rendering entry point**: `CanvasRenderer.render(recipe, RenderTarget)` — headless, isolate‑safe. `RenderTarget.preview/print` exist but **no stage branches on `quality`** (no supersampling tier yet).

## 3. Studio capabilities that directly support the experience

- **A reproducible genome + content‑hash IDs** → free undo/branch/compare/reorder: any design state is just a `recipeId`.
- **Named RNG sub‑streams** → the basis for "change one thing, keep the rest" once a re‑roll API is added.
- **Orthogonal Genre/Style/Effects axes** → map cleanly to customer‑legible creative decisions (subject vs vibe vs finish).
- **Preference stack + delete‑to‑learn** → the authoring stream (choose/reject/lock/favourite/buy) becomes training signal with no extra UI.
- **Travel model baked into recipes** → designs are *about the journey*, not generic art with flags added.
- **Headless renderer** → isolate‑friendly low‑res previews, deterministic caching by `recipeId@size`.
- **Reproducible library** → saved/liked/used‑for‑tshirt already modelled and persisted.

## 4. Capability gaps (must be extended in Design Studio)

1. **No incremental single‑axis re‑roll / lock API** on `DesignRecipe` (only whole‑batch `VariationGenerator`). *Foundational for the whole UX.*
2. **Garment colour not composited**; `ColourStrategy.garmentAware` unimplemented; no semantic‑lock vs adaptive tagging of elements.
3. **No front/back / print‑placement concept** in the recipe.
4. **Typography is inert + no bundled fonts** — editable text needs a real Typography stage and curated fonts.
5. **No real low‑res‑preview vs high‑res‑print path** (RenderQuality unbranched; no supersampling).
6. **No production print export from a `DesignRecipe`** (the studio writes flat PNGs; print files/DPI/placement live only in the mobile path).
7. **No quality gate** beyond diversity/learning.
8. **Asset delivery is dev‑only** (reads repo files from disk; no shared on‑device asset package).

## 5. Current T‑shirt UX limitations

- **Gallery‑and‑shuffle is the whole experience** — the brief explicitly rejects "repeatedly pressing generate." Authorship is weak: the customer *chooses among* the system's ideas rather than *directing* one.
- **No progressive evolution** — you cannot take one design and shape it decision‑by‑decision; "More like this" produces a fresh grid, not an edit of *this* shirt.
- **No lock/branch/compare** — exploring means regenerating and losing the thing you liked.
- **Garment colour is bolted on** at checkout rather than being a creative decision that adapts the artwork intelligently.
- **Text is not customer‑authored** and there is no AI title assistance surfaced in the flow.
- **Front/back is a downstream placement detail**, not part of a coherent "one garment" authoring model.
- **Two engines** mean the interactive brain (forge) and the thing that actually prints (CardImageRenderer) can drift.

## 6. Alternative UX models considered

| Model | Summary | Verdict |
|---|---|---|
| **A. Wizard / funnel** (Genre→Style→Effect) | Already exists in the Lab. Linear grid‑pick steps. | ✗ Feels like a config form; brief rejects wizards as the default. Keep as an *optional* "start from scratch" path. |
| **B. Generative gallery + shuffle** (today's mobile) | Auto‑designs grid, favourite, shuffle. | ✗ As the *whole* experience — the rejected "press generate repeatedly." ✓ Excellent **cold‑start seeder**. |
| **C. Taste‑swipe calibration** (Tinder‑style) | Swipe designs to seed preferences. | ◐ Great for the *first 20 seconds* / cold start; not authorship. Reuse the existing `preference_survey_screen` here. |
| **D. Pro direct‑manipulation canvas** | Drag/resize/layer elements. | ✗ Violates "not a pro editor," "mobile‑first." ✓ Reserve a *subset* (nudge/scale a chosen element) for refinement. |
| **E. Studio Canvas — evolving hero + creative decisions** | One hero design that transforms through a few meaningful choices; lock/branch/compare; progressive disclosure. | ✓ **Recommended.** Best fit for "I directed a designer and made this." |

## 7. Recommended interaction model — the "Studio Canvas"

A single screen whose **hero is always the shirt**. Structure:

1. **Instant hero.** On entry, the studio renders *one* strong design from the customer's travel context (seeded by `DesignContext.fromTrips`, ranked by `LabSmartGenerator`/preferences). No empty state, no grid to pick from.
2. **A rotating deck of creative decisions.** Below the shirt, a small, changing set of **tactile choice chips** — each a *concept the customer understands*, each backed by a recipe axis:
   - **Direction** (subject): flags · passport · your route · landmarks · a bold word — *Genre axis*.
   - **Vibe** (finish): vintage · surf · streetwear · minimal · maximal — *Style axis / StyleCluster*.
   - **Focus**: which countries lead, how busy, portrait/landscape — *composition/content axes*.
   - **Colour**: garment colour that *re‑inks* adaptive elements — *palette + garmentAware*.
   - **Words**: your title/phrase, or an AI suggestion — *typography axis*.
   Selecting any chip **immediately re‑renders the shirt** by constraining/re‑rolling **only that axis** (named sub‑stream), leaving everything else stable — the "evolve, don't regenerate" feeling.
3. **Alternatives tray.** A horizontal strip of 3–4 *interpretations of the current decision* (e.g. four vibes). Tapping one previews it live; it does not commit until you keep it — so exploration never destroys the current shirt.
4. **Lock.** Long‑press any decision to 🔒 pin it; future re‑rolls hold it fixed. This is the "preserve what I like" primitive.
5. **Branch + undo.** Every state is a `recipeId`; a breadcrumb of recent states gives instant undo and "branch from here." No work is ever lost.
6. **Two sides, one garment.** A Front/Back toggle on the shirt; both share a *theme* (palette/vibe/travel context) so the garment feels coherent, not two unrelated images.
7. **Progressive disclosure → Refine.** A "Refine" affordance opens finer controls (exact text, effect intensity, per‑element nudge, per‑country emphasis) for the minority who want them — never shown up front.
8. **Done.** A clear "This is the one" → garment colour/size → the existing mockup/checkout, carrying the exact `DesignRecipe`.

Cold start: optionally precede step 1 with a 15‑second **taste swipe** (reuse `preference_survey_screen`) — skippable — to seed `DesignPreferences`.

## 8. Why this model is preferable (against the core criterion)

*User authorship + creative exploration + Studio capability + design quality + simplicity + performance + uniqueness + printability.*

- **Authorship**: the customer makes a *sequence of their own decisions*; the shirt visibly becomes theirs.
- **Exploration without loss**: deterministic `recipeId`s make lock/branch/undo/compare essentially free.
- **Design quality**: every choice is a *curated axis value* inside the studio's grammar — the customer cannot produce an ugly/illegal combination (studio acts as the invisible expert; diversity + preference guardrails apply).
- **Simplicity / mobile**: 5 legible concepts, one screen, touch‑native chips and a swipe tray; complexity is disclosed only on request.
- **Performance**: single‑axis re‑roll + recipe cache means most interactions are a cache hit or one cheap re‑render, not a full batch regenerate.
- **Uniqueness**: procedural sub‑stream variation means two customers making the same 5 choices still get intentional, distinct artwork.
- **Printability**: the output is always a `DesignRecipe` → the proven print path; determinism guarantees reorder/reprint fidelity.

## 9. Proposed user journey

The journey is organised as **six phases on one always-visible canvas**, not a linear
wizard. The shirt is the hero throughout; the "steps" are decisions and tools available
in context. A first-timer can be walked A→F once as a light guided pass, but nothing is a
mandatory dead-end screen.

| Phase | What happens | Studio mechanism |
|---|---|---|
| **A · Start (instant)** | *Your Journey* auto-loads visited countries (optionally pick a trip / date range). A strong **hero front design appears immediately** on a sensible default garment — no blank canvas, no colour-first. | `DesignContext.fromTrips` → `LabSmartGenerator` |
| **B · Shape it** (non-linear, live) | Five always-available decisions, each re-renders instantly, each with an **alternatives tray + 🔒 lock**: **Direction** (subject/genre) → **Vibe** (finish) → **Focus** (which countries lead / busyness / orientation) → **Colour** (live, garment-aware) → **Words** (your text + AI ideas, offline fallback). | one recipe axis per decision (M2 re-roll) |
| **C · The other side** | Flip to **Back** — auto-derived to share the front's theme; same five decisions. | `GarmentDesign` shared theme (M7) |
| **D · Review** | Front + back together; change **garment colour once, across both sides** (smart contrast). | garment-aware colour (M5) |
| **E · Refine** (optional / Advanced) | Fine controls — position/scale/layers, effect intensity, per-country emphasis. Progressive disclosure only. | recipe parameter editing |
| **F · Done** | **Save to Collection · Add to cart · Share.** Design persisted as a reproducible recipe → print export → Printful. | `DesignLibrary`, print adapter (M1) |

```
A. Your Journey ─► INSTANT hero front design (already personal, default garment)
        │
   (optional taste-swipe seeds DesignPreferences first)
        ▼
B. Shape it — Direction · Vibe · Focus · Colour · Words   [shirt always visible]
        │  each decision = re-roll/constrain ONE axis, live re-render
        │  alternatives tray (non-destructive) · lock 🔒 · branch · undo
        ▼
C. Flip to Back (auto-derived, shares theme) ─► same five decisions
        ▼
D. Review both sides ─► garment colour once, across both (smart contrast)
        ▼
E. (optional) Refine — position/effects/emphasis (progressive disclosure)
        ▼
F. Save to Collection · Add to cart · Share
        │
        ▼  DesignRecipe persisted (recipeId) → print export → Printful
```

### 9a. Reconciliation with the ChatGPT storyboard

A hand storyboard (`~/Downloads/tshirt-design-storyboard.png`) sketched a 12-screen guided
flow. Its **"Behind the Scenes" panel maps 1:1 to this architecture** (Design Studio Engine
= procedural generation; Smart Contrast = `ColourStrategy.garmentAware`; Your Creative
Recipe = deterministic `DesignRecipe`; Print Ready = `createMerchCart`/Printful) — strong
validation of the model. Kept from it: front+back as first-class, remix scoped by axis with
*"keep other settings the same"* (= single-axis re-roll + lock), AI text with a
suggestions list + "generate more", colour preview with automatic contrast, save/share.
**Adjusted** to fit the brief's "no wizard / shirt-is-hero / progressive creation":

- **Colour 3→1.** The storyboard chose colour three times (steps 2, 7, 11) and *before any
  design existed*. Colour becomes one always-available live decision; never colour-first.
- **AI text 2→1.** One capability inside the Words decision, on both sides (storyboard had
  it at steps 4 and 10).
- **Editing surfaces 3→1 (+optional Advanced).** *Customize*, *Refine & Position* (a
  desktop move/scale/rotate/flip/layers surface) and *Remix* collapse into contextual
  decisions; the pro direct-manipulation surface becomes optional Phase E.
- **Add an explicit Direction (genre) choice** — the storyboard's design just "appeared";
  the largest creative axis (flags vs stamps vs map vs timeline vs word) must be a decision.
- **Surface lock / undo / branch** explicitly (the storyboard only implied it via "keep
  other settings").
- **"Put it on a T-shirt" → Add to cart.** It already is a t-shirt; the terminal action is
  order/checkout.
- **"Remix & Explore" is not a step** — it is the per-decision alternatives tray plus a
  global "Surprise me" always on the canvas.

## 10. Key screen concepts

- **Canvas (primary).** Shirt hero (front/back toggle), decision deck (chips), alternatives tray, breadcrumb (undo/branch), single primary CTA ("This is the one").
- **Alternatives tray.** 3–4 live thumbnails of the current decision's options; tap to preview, keep to commit.
- **Colour sheet.** Garment swatches that re‑ink adaptive elements live (flags keep their colours).
- **Words sheet.** Free‑text field + "Suggest" (AI titles from travel context, offline fallback bank) + case/placement.
- **Refine sheet (progressive).** Effect intensity sliders, per‑country emphasis, element nudge/scale, edge/finish detail.
- **Confirm.** Front+back mockup, colour/size, price, add to cart.

## 11. Interaction behaviours

- **Immediate feedback:** every committed decision re‑renders < ~300 ms (preview res, cached where possible).
- **Non‑destructive preview:** tapping an alternative shows it but does not commit until "keep."
- **Lock:** locked axes are held across all subsequent re‑rolls and shown with a 🔒 chip state.
- **Branch/undo:** breadcrumb of `recipeId`s; undo = re‑select a prior id (instant, cached); branch = continue from a prior id.
- **Coherent sides:** switching front/back keeps shared theme; a "match front" affordance derives the back from the front's theme.
- **Learning:** choose (styleChosen/selectedForMockup), reject alternative (rejected), lock+vary colour (shape‑stable signal), favourite (saved), buy (strong positive) — all folded into `DesignPreferences` via the existing learner; intrusive prompts avoided.

| Vibe | Style finish (`edge`,`effects`,`palette`) | `StyleSpec.finish`; StyleCluster | styleChosen |

## 13. Recommended architecture

```
Travel data (TripRecord) ─► DesignContext ─► LabSmartGenerator (seeded, preference-ranked)
                                              │
                                              ▼
                                   DesignRecipe  ◄─────────── single source of truth (content-hash id)
                                   │        ▲
        interactive edits ────────►│        │ recipe cache (recipeId@size)
   (re-roll/constrain ONE axis)    │        │
                                   ▼        │
                 ┌─────────── Preview path ─┴──────────┐        Print path
                 │  design_forge_render (headless,     │   DesignRecipe ──► recipe→DesignParams adapter
                 │  isolate, low-res, deterministic)   │        ──► CardImageRenderer (pixelRatio 12)
                 └─────────────────────────────────────┘        ──► PrintStylePipeline ──► createMerchCart ──► Printful
                                   │
                                   ▼
                         PreferenceLearner ◄── authoring signal stream ── UX
```

Principles:
- **`DesignRecipe` is canonical.** Production `DesignParams` becomes a *derived, render‑only* artifact via an adapter; the recipe (JSON + `recipeId`) is what is persisted, shared and reordered.
- **Two render targets, one genome.** Interactive **preview** uses `design_forge_render` in an isolate (fast, deterministic, cache‑friendly). **Print** initially routes through the mature `CardImageRenderer`/`PrintStylePipeline` via the adapter (no rewrite of the print path). Over time, extend `design_forge_render` to print parity and collapse to one renderer.
- **Extend, don't fork.** New capabilities (axis re‑roll, garmentAware, front/back, Typography stage) are added *inside* `design_forge`/`design_forge_render`, not in a parallel generator.

## 14. State / data‑model implications

- **`GarmentDesign`** (new composite, canonical unit of a product):
  `{ front: DesignRecipe?, back: DesignRecipe?, garmentColour, variant(size), themeSeed, sharedPalette/context }`.
  Front and back are two recipes sharing a theme so the garment reads as one product.
- **`DesignRecipe` extensions:** a `placement`/`side` concept for print‑area; a `garmentAware` palette strategy that actually renders; `typography` becomes live; per‑element **semantic‑lock vs adaptive** tags for contrast.
- **Edit session state:** `{ currentRecipeId, lockedAxes:Set, breadcrumb:List<recipeId>, side }` — thin, since every state is reproducible from an id.
- **Persistence:** store the full `GarmentDesign` (both recipe JSONs + colour/variant) in the `MerchConfig`/library so reopen/reorder/reprint reproduce exactly. Extend the delete‑to‑learn library to garments.

## 15. Rendering / performance strategy

- **Isolate preview renderer** using `design_forge_render` at preview resolution; **cache by `recipeId@size`** (undo/compare become cache hits).
- **Implement the RenderQuality branch**: preview = fast/low supersample; print = supersampled 1800×2400. (Today `quality` is inert.)
- **Incremental re‑roll** avoids full‑batch regeneration; only the changed axis redraws.
- **Debounce & pre‑render** the alternatives tray in the background while the customer looks at the hero.
- **Battery/heat:** cap concurrent renders (existing thumbnailer is concurrency‑1), reuse cached tiles, avoid re‑rasterising flags per frame (the render layer already caches flags by `code@WxH`).
- **Print stays server‑capable:** the `createMerchCart` Sharp path already produces the final print file; the client sends the high‑res recipe render.

## 16. Front / back approach

- Model both sides as **two `DesignRecipe`s inside one `GarmentDesign`** sharing a `themeSeed`, palette and travel context.
- Default: **auto‑derive a complementary back** from the front's theme (e.g. front = bold word / chest ribbon, back = full travel design) so first‑time users get a coherent two‑sided garment with zero extra effort.
- The mobile print path already supports front placement (chest ribbon @525px) + full‑area back — the adapter maps `GarmentDesign.front/back` onto those slots.
- UI: a Front/Back toggle on the shirt hero; edits apply to the visible side; a "match front" action re‑themes the back.

## 17. Text & AI‑assistance approach

- **Text is a first‑class recipe element**: build the currently‑inert **Typography stage** and **bundle curated display fonts** (the `pubspec` font block is presently commented out). Customer types their own wording; case/placement are recipe fields.
- **AI as optional creative assistant, never renderer**: a "Suggest" action asks an AI for short travel titles from the selected countries/context; suggestions are *strings that become recipe text*. Must respect the existing title‑generation rules (one ready‑to‑go title, no numbering/preamble, no single‑country name for multi‑country, varies each press).
- **Fully functional offline**: a curated phrase bank provides suggestions when AI is unavailable; nothing in the render path depends on AI.

## 18. Garment colour / contrast strategy

- Garment colour becomes a **design‑level property** that flows into `RenderTarget.background` *and* triggers a **`garmentAware` contrast pass** (implement the declared‑but‑empty `ColourStrategy.garmentAware`).
- **Adaptive vs semantic‑locked elements:** typography, line art, passport‑stamp ink, borders, decorative strokes, silhouettes **adapt** for contrast (the mobile renderer already derives ink from shirt luminance — reuse that logic). **Flags and intentionally‑coloured artwork keep their semantic colours.** No global invert.
- Colour is therefore a *creative* decision that visibly re‑inks the shirt, while remaining the checkout variant it already is.

## 19. Preference‑learning opportunities

Turn the authoring stream into non‑intrusive signals via the **existing** `PreferenceLearner`:

| Action | Signal |
|---|---|
| Keep a decision / open to refine | `styleChosen` / `selectedForMockup` |
| Reject an alternative in the tray | `rejected` (−0.5) |
| Lock an axis then vary another | reinforce the locked feature (stability) |
| Favourite / save | `saved` |
| Add to cart / buy | strong positive (usedForTshirt) |
| Delete‑to‑learn (already built) | batch `observeBatch` rework |

These feed `DesignPreferences`, which ranks the next hero and the alternatives tray, so the studio *gets better for that customer over time* — reusing, not duplicating, the recommendation stack. The written‑but‑unwired `PreferenceBridge`/`recommendSmart`/`preference_survey_screen` are the natural connectors.

## 20. Production / print implications

- The canonical unit persisted to `MerchConfig` becomes the `GarmentDesign` (both recipe JSONs + colour + variant), so any order is fully reproducible and reorderable.
- Print export continues through `createMerchCart` (1800×2400 @150 DPI transparent, front+back placement, Printful v2) — fed by the recipe→DesignParams adapter, so **no print regression risk** in early milestones.
- Add **determinism tests** asserting `recipeId` → identical print `imageHash`, and that preview and print agree structurally.
- Longer term: move print rendering onto `design_forge_render` (once fonts + garmentAware + placement land) to collapse to one renderer.

## 21. Milestone implementation plan

Vertical, demonstrable, additive to Design Studio, no duplicate design logic. Each builds on the last.

- **M1 — Unify the genome (spine).** Make `DesignRecipe` the source of truth on mobile; build the `DesignRecipe → DesignParams` **adapter** so a forge recipe renders + prints through the existing pipeline; wire the already‑written `recommendSmart` live so the current Auto‑designs gallery is forge‑driven. *Demo:* today's gallery, now powered by the studio, still prints correctly. *Files:* `procedural_design_service.dart`, new adapter, `procedural_recipe.dart`. *Tests:* adapter round‑trip legality; determinism (recipe→params→render hash stable).
- **M2 — Incremental axis re‑roll + recipe cache.** Add a studio API to re‑roll/constrain **one** named axis holding others fixed; add `recipeId@size` render cache. *Demo (Lab):* change one axis live, everything else stable; instant undo. *Files:* `design_forge` generator, `render_service`/isolate cache. *Tests:* re‑rolling axis A leaves axes B..N byte‑identical.
- **M3 — Studio Canvas MVP (vertical slice on device).** Instant hero + decision deck (Direction/Vibe/Focus) + live re‑render + breadcrumb undo. *Demo:* evolve one shirt through 3 decisions on iPhone. *Files:* new `studio_canvas_screen.dart`, preview isolate. *Tests:* widget tests for deck→re‑render; golden of hero for a fixed seed.
- **M4 — Lock / branch / alternatives + learning.** Alternatives tray, per‑axis lock, branch; wire the decision stream into `PreferenceLearner` (+ existing delete‑to‑learn). *Demo:* explore without losing work; next hero reflects taste. *Tests:* lock invariance; signal‑fold updates preferences.
- **M5 — Garment colour as design.** Implement `ColourStrategy.garmentAware`; semantic‑lock vs adaptive tagging; live colour sheet that re‑inks adaptive elements only. *Demo:* switch Black→White, flags keep colour, text/stamps re‑ink. *Tests:* flags unchanged; adaptive elements meet a contrast threshold.
- **M6 — Text as material + AI titles.** Bundle fonts; build the Typography render stage; in‑canvas text entry; "Suggest" titles (AI + offline bank, respecting title rules). *Demo:* type/AI a title, see it on the shirt; works offline. *Tests:* Typography stage renders real glyphs (non‑Ahem host); offline fallback path.
- **M7 — Front & back as one garment.** `GarmentDesign` composite, shared theme, side toggle, auto‑derived back; both sides flow to print export. *Demo:* two coherent sides, both print. *Tests:* shared‑theme invariants; both placements exported.
- **M8 — Production hardening.** RenderQuality supersample branch; reorder/reprint from stored `GarmentDesign`; performance (isolate preview, capped concurrency, battery); print parity determinism suite. *Demo:* reorder reproduces exactly; smooth on device. *Tests:* recipeId→print hash stable; perf budget.

*(Optional M0 — Taste‑swipe cold start: wire the existing `preference_survey_screen` as a skippable opener seeding `DesignPreferences`.)*

## 22. Tests & acceptance criteria

- **Determinism:** identical `GarmentDesign` ⇒ identical preview + print `imageHash`; reorder reproduces byte‑for‑byte.
- **Axis isolation:** re‑rolling one axis leaves all other axes' contributions unchanged (hash‑diff bounded to that axis).
- **No‑loss exploration:** undo/branch always returns to an exact prior state; committing an alternative never mutates un‑previewed axes.
- **Garment contrast:** flags/semantic art unchanged across colours; adaptive elements pass a measured contrast ratio on each garment colour.
- **Typography:** renders real letters on a font‑bundled host; offline suggestion path works with AI disabled.
- **Print parity:** recipe→DesignParams→print file matches the studio preview structurally; front+back placement correct at 1800×2400.
- **Learning:** reject/keep/buy measurably move `DesignPreferences`; delete‑to‑learn batch reworks as today.
- **Performance:** committed decision re‑renders within budget on a mid‑range iPhone; no runaway battery/heat under a 5‑minute session.
- **Acceptance (experience):** in usability testing, users describe the result as *"I made this"* and can (a) evolve a shirt through ≥3 decisions, (b) lock something and keep it, (c) undo, (d) design a back, (e) change garment colour sensibly, (f) add their own words — without instruction.

## 23. Risks & unresolved technical questions

1. **Two renderers drifting.** Preview (`design_forge_render`) and print (`CardImageRenderer`) can diverge. *Mitigation:* the recipe is canonical; add a parity test; plan eventual single‑renderer convergence (post‑M8).
2. **Axis‑isolation vs draw order.** Because sub‑streams derive from one seed, changing an input that alters *draw order* can shift other axes. *Open Q:* do we need per‑axis seeds (a seed vector) rather than one seed? Likely yes for true lock — decide in M2.
3. **On‑device assets.** `FlagSource` reads repo files; mobile needs a **shared bundled asset package**. *Open Q:* size/packaging of flags+silhouettes+stamps for the app bundle.
4. **Fonts.** Licensing + bundle size for curated display fonts; headless isolate must register them or fall back to Ahem. *Open Q:* which font set, and isolate font registration.
5. **garmentAware tagging.** Which elements are "semantic‑locked" vs "adaptive" must be encoded in the recipe/grammar. *Open Q:* per‑element metadata vs per‑family rules.
6. **Front/back print mapping.** The mobile front slot is a small chest ribbon; not every genre suits it. *Open Q:* which genres are valid front vs back, and the default back‑derivation rule.
7. **AI latency/cost/offline.** Title suggestions must never block; ensure graceful offline. *Decided:* offline phrase bank fallback; AI strictly assistive.
8. **Perf of live re‑roll on device.** Isolate + cache should suffice, but effect‑heavy recipes (halftone/shatter) are costly. *Open Q:* preview‑res effect approximations vs full effects at commit time.
9. **Migration.** Existing saved/ordered `DesignParams` designs predate recipes. *Open Q:* backfill via `ProceduralRecipeCodec.fromFlatJson` (already exists, lossy) vs treat as legacy‑render‑only.
